# Hourly Demand & Restaurant Performance Analytics: Power BI Dashboard and Demand Forecasting

## Project Overview

This project combines two parts of food delivery analytics: a Power BI dashboard for analyzing historical order data and a Python-based forecasting notebook for estimating future demand.

The dashboard focuses on descriptive analytics. It shows how order volume changes across different times of the day, restaurants, cities, and account manager portfolios. The forecasting notebook extends this work by using historical order patterns to predict future demand.

The dashboard is a portfolio recreation of a dashboard I originally built for my employer. I recreated it using synthetic data so that I could publish the project without exposing confidential business information. The forecasting work was developed independently using synthetic data.

> **Note on data:** All company names, restaurant names, staff names, and order records in this repository are synthetically generated. They do not represent any real business, person, or transaction. The original dashboard, which used actual company data, is confidential and is not included in this repository. See [Data Disclaimer](#data-disclaimer) for more details.

## Business Problem

Food delivery operations involve managing order demand across different time periods, locations, and restaurant partners. During my work with food delivery data, I needed to answer several recurring operational questions:

- At what times of the day does the platform receive the most orders?
- How does order volume change throughout the month for individual restaurants?
- Which cities contribute the most orders?
- How much order volume is generated by each account manager's restaurant portfolio?
- Does order volume follow a recurring pattern across Sundays?

The dashboard brings these views together in one report. It uses order-level transaction data and a restaurant master list, which are transformed in Power Query and connected in the Power BI data model.

## Project Objectives

1. Create a repeatable Power Query workflow to load order-history exports and a restaurant master file.
2. Build a simple star-schema data model using an order fact table and a restaurant dimension table.
3. Create hourly, 30-minute, and 15-minute time buckets so order demand can be analyzed at different levels without duplicating the underlying data.
4. Build interactive report pages with slicers that allow users to explore the data without writing queries.
5. Create a Sunday comparison view that identifies each Sunday's occurrence within its month, making it possible to compare the first, second, third, and fourth Sundays across the dataset.

## Data Model

The report uses two main tables.

**Tables**

- **sample_orders (fact table):** Contains 25,000 synthetic order records, with one row representing an individual order transaction.
- **sample_restaurant_master (dimension table):** Contains 450 synthetic restaurant-branch records. It includes chain and restaurant names, city, cuisine, account manager, commission percentage, and restaurant status.
- **Date tables:** Power BI automatically generates date tables for the date fields used in slicers.

**Relationship**

The two main tables are connected through the restaurant branch ID.

```text
sample_orders[Restaurant Branch ID]  *  ──────  1  sample_restaurant_master[restaurant_branch_id]
               (many)                                          (one)

Cardinality: Many-to-One
Cross-filter direction: Single
Relationship status: Active
```

I used a simple two-table star-schema structure. The order table stores the transaction details, while the restaurant table contains information such as restaurant name, city, and account manager. This allows the report to analyze order volume using the attributes in the restaurant table.

## Power Query Transformations

I used Power Query to load and prepare both CSV files before building the data model.

**sample_orders table**

- Loaded the order data from a CSV export.
- Applied explicit data types to the columns, including dates, decimal amounts, whole numbers, and boolean values.
- Added a `Month Name` column using `Date.MonthName`.
- Added a `Date` column using `DateTime.Date` to remove the time component and support date-level filtering.

**sample_restaurant_master table**

- Loaded the restaurant master data from a CSV export.
- Promoted the first data row to column headers.
- Applied explicit data types to the columns.

The full M code, including explanations of the transformations and the original folder-based ingestion approach, is available in [`docs/power_query_transformations.md`](docs/power_query_transformations.md).

## DAX Measures and Calculated Columns

I used explicit DAX measures for the main report calculations and calculated columns for the different time intervals and Sunday comparisons.

**Explicit measures**

| Measure | Logic |
|---|---|
| `Total Orders` | `COUNTROWS('sample_orders')` |
| `Total Revenue` | `SUM('sample_orders'[Total Amount])` |
| `Avg Order Value` | `DIVIDE([Total Revenue], [Total Orders])` |
| `Cancellation Rate %` | Share of orders with status `cancelled`, `restaurant_rejected`, or `not_delivered` |

**Calculated columns**

| Column | Table | Logic |
|---|---|---|
| `1 Hour Range` | sample_orders | Groups orders into hourly intervals, such as `13-14`. |
| `30 Min Range` | sample_orders | Groups orders into 30-minute intervals, such as `13:30-14:00`. |
| `15 Min Range` | sample_orders | Groups orders into 15-minute intervals, such as `13:15-13:30`. |
| `1 Hour Sort` / `30 Min Sort` / `15 Min Sort` | sample_orders | Numeric helper columns based on minutes since midnight. These allow the time-range columns to be sorted chronologically using Power BI's Sort by Column feature. |
| `Sunday Occurrence` | sample_orders | Checks whether a date is a Sunday using `WEEKDAY(d,1) = 1`. If it is, `ROUNDUP(DAY(d)/7, 0)` identifies its occurrence within the month and labels it as `Sunday 1`, `Sunday 2`, and so on. Non-Sundays return blank. |

The `Sunday Occurrence` column is used on the Sunday Comparison page. It allows Sundays from across the dataset to be compared by their position within the month, rather than limiting the comparison to only the two most recent Sundays.

The complete DAX code with explanatory comments is available in [`docs/dax_measures.md`](docs/dax_measures.md).

## Demand Forecasting Notebook (Python / Machine Learning)

I extended the project beyond the dashboard by developing a separate demand forecasting notebook using Python and scikit-learn.

The dashboard shows what happened in the historical order data. The forecasting notebook uses those historical patterns to estimate what order demand might look like in future periods.

The notebook is available at [`notebooks/demand_forecasting.ipynb`](notebooks/demand_forecasting.ipynb).

### Dataset

The forecasting notebook uses approximately 25,000 synthetic order records covering January to May 2026. The dataset includes order timestamps, restaurant information, and promotional usage data.

For the hourly forecasting task, I grouped all order records by hour. The target is the total number of recorded orders across the platform in each hour, regardless of order status. It is not a forecast of completed deliveries only.

### Forecasting Tasks

| Track | Prediction | Granularity |
|---|---|---|
| **A: Platform-wide hourly demand** | Total recorded order volume across the platform | Orders per hour |
| **B: Restaurant-level daily demand** | Daily order volume for the ten highest-volume restaurant branches, selected using training-period data only | Orders per restaurant-day |

### Methodology

Both forecasting tasks followed this workflow:

EDA → feature engineering → chronological train-test split → baseline forecasting → Random Forest and Gradient Boosting training → MAE evaluation → error analysis.

The features included time-related variables, lag features, rolling averages, promotional usage, and restaurant attributes where applicable. I used a time-based split rather than a random split so that the models were trained on earlier observations and evaluated on later ones.

### How the Models Are Evaluated

Both tasks use a rolling one-step-ahead setup, not a single forecast made once at the start of the test period.

The lag and rolling features are built from actual past order counts across the full time series, before the split. Each test-period prediction can therefore use the actual order count from the preceding period. For example, a prediction for May 4 at 20:00 can use the actual order count for May 3 at 20:00, 24 hours earlier. Similarly, a restaurant's daily prediction can use its actual order count from the previous day.

This setup is appropriate when actual order counts become available before each new prediction is made. It is different from forecasting an entire future month using only information available on the first day of that month.

### Data Preparation and Evaluation Checks

Several checks were important for making the forecasting comparisons consistent:

1. **Complete hourly timeline:** Included hours with zero orders so that `Lag_24h` consistently refers to the same hour on the previous day.
2. **Restaurant identification:** Used `Restaurant Branch ID` rather than restaurant names for grouping and merging, since different branches can share the same name.
3. **Lag and rolling features:** Calculated lag features and rolling averages before removing rows with insufficient historical data.
4. **Training-period selection:** Selected the ten highest-volume restaurant branches using training-period data only and applied the same cutoff date to restaurant selection and model evaluation.
5. **Promotional features:** Used the previous day's promotional usage rate to avoid including information from the prediction day.
6. **Consistent evaluation:** Verified that Random Forest and Gradient Boosting were evaluated on identical restaurant-level test observations, dates, branch IDs, and target values.

### Model Results

| Forecasting task | Baseline MAE | Best ML MAE | Result |
|---|---:|---:|---|
| Platform-wide hourly | 2.53 | 1.88 (Gradient Boosting) | 26% improvement |
| Restaurant-level daily | 0.54 | 0.53 (Gradient Boosting) | 1.2% improvement |

For platform-wide hourly forecasting, Gradient Boosting reduced MAE by approximately 26% compared with the baseline. Random Forest also performed better than the baseline, but Gradient Boosting achieved the lowest error.

For restaurant-level daily forecasting, Gradient Boosting reduced MAE by approximately 1.2%, while Random Forest performed approximately 1.5% worse than the baseline. Both models were evaluated on the same 300 restaurant-day observations, covering the same restaurants and test period.

The restaurant-level results are close to the baseline. Given the small difference and the limited dataset, I would not interpret this as evidence of a reliable improvement.

### Notable Findings

- For Track A, Random Forest identified `Lag_24h` as its most important feature, followed by `Hour`. This suggests that the previous day's demand at the same hour was particularly informative for estimating hourly order volume.
- For Track B, the strongest Random Forest features were `commission_pct`, `Rolling_7day_avg`, and `Weekday`. Since the model performed similarly to the baseline, these feature rankings should be interpreted cautiously.
- Random Forest's two largest hourly prediction errors occurred on May 21 and May 22. I examined the data generation logic and found no specific events associated with those dates, so the errors may reflect random variation.
- Track B's largest errors occurred on different dates, including May 23 and May 11, rather than showing a similar pattern across both forecasting tasks.

Feature importance and error analysis are based on Random Forest. Although Gradient Boosting achieved the best hourly forecasting result, these two analyses were not performed on that model.

### Limitations

The forecasting models use synthetic data rather than actual company order records, so the results should not be treated as evidence of real-world forecasting performance.

The models were evaluated using a rolling one-step-ahead setup on a held-out period from the same synthetic dataset, not on an independent real-world dataset or a true multi-period-ahead forecast. The test period was also inspected during iterative data-quality corrections and model comparisons, so it should be treated as an exploratory temporal holdout rather than an untouched final benchmark.

The models do not account for external factors such as holidays, weather, or unexpected changes in customer behavior. They estimate expected order volume based on historical patterns but do not measure the causal effect of promotional campaigns or other business decisions.

For restaurant-level daily forecasting, the evaluation covers ten restaurant branches over approximately five months of data. This may not be enough to establish a reliable advantage over a simple baseline. A larger number of restaurants, a longer time period, and additional external features would be useful next steps.

## Key Insights

*The following patterns are based on the synthetic data included in this project. They should not be treated as findings about the original company or any real food delivery platform.*

- Order demand is concentrated around two periods: a smaller midday peak and a larger evening peak. This is visible in the 15-minute and hourly charts.
- A relatively small number of restaurants account for a large share of total order volume.
- Order volume varies across cities, which can be useful when considering location-level operational planning and rider allocation.
- The Sunday Comparison page allows users to compare order volume across successive Sundays within a month. This can help identify recurring patterns that may be relevant to staffing decisions.

## Future Improvements

- Create a dedicated Date dimension table and mark it as the official Date table instead of relying on Power BI's automatic date/time tables.
- Add year-over-year and month-over-month percentage change measures using `DATEADD` and `SAMEPERIODLASTYEAR`.
- Add a delivery-time KPI card. The raw data already contains delivery-time information, but it is not currently visualized.
- Implement row-level security (RLS) so that each account manager can access only their own restaurant portfolio in a shared workspace.
- Add a map visual to show the geographic distribution of order demand across cities.
- Add a short walkthrough of the Power BI report using a GIF or screen recording.
- Test the forecasting models against a fully independent dataset.
- Include an event and holiday calendar in the forecasting models to account for external factors that may explain unusual demand patterns or prediction errors.
- Extend restaurant-level forecasting beyond the top ten restaurants. For restaurants with very sparse order histories, a classification approach that predicts whether a restaurant will receive any orders on a given day may be more suitable.

## Data Disclaimer

The `/data` folder contains fully synthetic data generated using the Python script `data_generator_script.py`, which is included in this repository.

The generated data is designed to follow the general structure and statistical patterns of the original dataset, including order volumes, time-of-day patterns, and order amount distributions. No real restaurant, customer, rider, or employee data is included.

Some original column names, such as `Foodi Burn`, which referred to a brand-specific subsidy metric, were replaced with generic names such as `Platform Subsidy`. Real employee and account manager names, restaurant chain names, customer phone numbers, and file paths from the original workbook were also replaced or removed.
